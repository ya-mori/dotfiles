# 対外メッセージ ドラフト作成スキル

Slack 返信・メール・問い合わせ・依頼など、**社外/他チーム/他者宛のメッセージ** を作成するときに使う。
完成形をいきなり書かず、2段階の承認を経て意図のズレを防ぐ。

---

## 重要な原則

- **完成形をいきなり書かない**。タイプと骨組みの2段階承認を必ず経る
- **タイプを間違えると後段が全部ズレる**。タイプ確認なしに「説明する」前提で書き始めない
- **推測・解釈はデフォルトで省略**。書きたい場合は明示的にユーザーに確認する
- **書き手の長文 > 読み手のコスト**。短く、事実 + 問い/依頼だけで完結させる

---

## 適用範囲

| 適用する | 適用しない |
|---|---|
| Slack 返信・投稿 | 社内ドキュメント |
| メール | 調査メモ |
| 問い合わせ回答 | レポート（詳細） |
| 依頼メッセージ | コードコメント |

---

## ワークフロー（4ステップ・順守必須）

### ステップ1: タイプ診断（スキップ禁止）

完成形を書く前に、目的タイプを番号選択で確認する。

| # | タイプ | 用途 | 構造 |
|---|------|------|------|
| 1 | 説明する / 報告する | 調査結果・進捗を伝える | 事実 + 結論 + 補足 |
| 2 | 依頼する | 相手に作業を頼む | 背景 + 依頼内容 + 期日 |
| 3 | 質問する | 相手から情報を引き出す | 事実 + 問い |
| 4 | 相談する | 一緒に方針を考える | 状況 + 選択肢 + 意見 |

推奨タイプを1つ提示し `y/n` で承認を取る。

### ステップ2: 相手の前提確認

以下を確認する（既に明らかな場合はスキップして良い）:

- **誰宛か**: 社外 / 他チーム / 同僚 / 上司
- **専門用語が通じるか**: 自分のチームの内部用語が通じる相手か
- **配信先ツール**: Slack / メール / Notion / その他

### ステップ3: 骨組み提示（スキップ禁止）

見出し・主要セクション名だけの骨組みを提示。本文の中身はまだ書かない。
ユーザーが「ここいらない」「ここ足して」を言いやすくする。

例:

```
- 挨拶
- 事実（数字の表）
- 問い ← ここがタイプ「質問する」の本体
```

`y/n` で承認を取ってから次へ進む。

### ステップ4: 肉付け

承認後に本文を書く。下記「本文の書き方」に従う。

---

## 本文の書き方（必須ガイドライン）

### 1. 「事実」と「依頼/問い」だけで完結させる

原因推測・解釈はデフォルトで省略する。書きたい時は明示的に
「推測パートを入れますか？」とユーザーに確認してから入れる。

**Why**: こちらの推測を相手に押し付けると、相手が反論しづらく対話を閉じてしまう。
問いを投げる形にすると相手側の意図を尊重できる。

OK/NG 例は `reference.md` 参照。

### 2. 専門用語は相手の前提知識レベルに合わせる

社外/他チーム宛の場合は、自分のチームの内部用語をデフォルト避ける。
相手が不明なときは前提知識をユーザーに確認する。

### 3. 短文 > 長文

読み手のコストを最小化する。書きたいことを全部書かない。

### 4. 表のレンダリングに注意

| 配信先 | 表の書き方 |
|---|---|
| Slack | コードブロックで等幅整形（markdown table は不可） |
| メール | HTML テーブル or プレーンテキストで整形 |
| Notion | `<table header-row="true">` 記法 |

## 送信前チェックリスト

ユーザーに最終ドラフトを渡す前にセルフチェック:

- [ ] タイプは合っているか（説明/依頼/質問/相談）
- [ ] 事実と問い/依頼だけで構成されているか（推測は最小限）
- [ ] 相手の前提知識に合った言葉づかいか
- [ ] 表は相手のツールでレンダリングされる形式か
- [ ] 短くできる箇所はないか
