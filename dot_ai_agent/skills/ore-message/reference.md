# 対外メッセージ ドラフト作成 リファレンス

`SKILL.md` の詳細・OK/NG 例・背景を記載。

---

## 背景：なぜこのスキルが必要か

Slack 返信ドラフトの作成で、意図のズレが3回続けて起きたことが発端。

- 1回目: 専門用語を使いすぎた（プロダクトの内部構造を知らない相手向け）
- 2回目: 推測を断定的に書きすぎた（原因を決めつけて書いたが、実投稿は「どういう粒度？」と問いだけ）
- 3回目: 表が Slack でレンダリングされない記法で書いた（markdown table）

ユーザーが実際に投稿したメッセージは、Claude の長い提案より遥かにシンプルで
「事実 + 問い」の構造だった。

このスキルの目的は、Claude のデフォルト（書きすぎ・推測を入れる・専門用語を使う）を
相手目線に矯正すること。

---

## 本文の書き方：OK/NG 例

例中の識別子・テーブル名は架空のもの。自分のプロダクトの用語に読み替えて使う。

### 例1: 推測を入れない

**OK 例**:
> 集計値が合いませんでした。どういった粒度の集計になっていますか？

**NG 例**:
> 集計値が合いませんでした。原因は重複を別カウントしているからで、本来は X 単位で集計すべきです。

**ポイント**: 事実 + 問い で完結。推測は省略。相手が原因を語れる余地を残す。

---

### 例2: 専門用語を避ける

**OK 例**（社外/他チーム宛）:
> 画像の枚数と取得元を教えてください

**NG 例**（社外/他チーム宛）:
> entity の item と source_item_id を教えてください

**ポイント**: 内部用語（テーブル名・カラム名・内部 ID などの識別子）は社外/他チーム宛では使わない。
相手が日常的に使っている言葉に置き換える。

---

### 例3: 表のレンダリング

**OK 例**（Slack 投稿）:
````
```
日付         | 件数 | 金額
2026-01-14  | 12   | ¥120,000
2026-01-15  | 8    | ¥80,000
```
````

**NG 例**（Slack 投稿）:
```
| 日付 | 件数 | 金額 |
|---|---|---|
| 2026-01-14 | 12 | ¥120,000 |
| 2026-01-15 | 8 | ¥80,000 |
```

**ポイント**: Slack は markdown table をレンダリングしないので、コードブロック内で等幅整形する。

## タイプ別の構造詳細

### 説明する / 報告する

```
- 結論（一行）
- 事実 / 数字
- 補足（必要なら）
```

### 依頼する

```
- 背景（なぜ依頼するか・一行）
- 依頼内容（具体的に）
- 期日 / 優先度
```

### 質問する

```
- 事実（何が起きているか）
- 問い（何を知りたいか）
```

### 相談する

```
- 状況
- 選択肢（複数）
- 自分の意見（あれば）
- 相手への問い
```

---

## タイプを間違えるパターン

| 起こりがちな誤判定 | 影響 |
|---|---|
| 「質問する」が本来なのに「説明する」と判定 | 推測・原因解釈を書き込んでしまう |
| 「依頼する」が本来なのに「相談する」と判定 | 期日が抜ける |
| 「相談する」が本来なのに「依頼する」と判定 | 選択肢が出ず、相手に押し付けがましくなる |

判定に迷ったらユーザーに確認する。書き始める前に止めるのが最も安い。

---

## このスキルの源流

Slack 返信ドラフトでの失敗から得たナレッジを元に作成。
原典は当時のプロジェクトの作業ログに残してある。
