# Smart Commit - 詳細ワークフロー

このドキュメントでは、Smart Commit スキルの8ステップワークフローを詳細に説明します。

## 概要

Smart Commit は以下の8ステップで実行されます：

0. 対象ディレクトリの取得
1. 作業計画の作成
2. 品質チェック（必須）
3. 未コミット状況確認
4. 変更内容のグループ化
5. コミット内容のレビュー
6. 適切な粒度でコミット
7. 品質確保
8. プロジェクトメモリ更新検討

各ステップを詳しく見ていきましょう。

---

## Step 0: 対象ディレクトリの取得

### 目的

コミット対象とするディレクトリまたはファイルのパスを特定します。

### 実行内容

1. **引数からパスを取得**
   - `$ARGUMENTS` 変数から対象パスを取得
   - 例: `/smart-commit src/auth` → `src/auth` を対象

2. **引数がない場合**
   - ユーザーに対象パスを確認
   - 何も指定されない場合はカレントディレクトリ（`.`）を使用

3. **パスの検証**
   - 指定されたパスが存在するか確認
   - Git リポジトリ内にあるか確認

### コマンド例

```bash
# カレントディレクトリの確認
pwd

# 対象パスの存在確認
ls -la {対象パス}

# Git リポジトリかどうか確認
git rev-parse --is-inside-work-tree
```

### エラーハンドリング

- **パスが存在しない場合**: ユーザーに通知し、正しいパスを確認
- **Git リポジトリ外の場合**: エラーメッセージを表示して終了
- **特殊文字が含まれる場合**: 適切にエスケープまたはクォート

### 出力

対象パスが確定し、後続ステップで使用されます。

---

## Step 1: 作業計画の作成

### 目的

実行する作業をタスクリストとして可視化し、進捗を管理します。

### 実行内容

1. **TaskCreate で作業をタスク化**
   - 品質チェックの実行
   - コード整理（不要なコメント・デバッグコード削除）
   - 未コミット状況の確認
   - 変更内容のグループ化
   - コミットの作成
   - プロジェクトメモリ更新の検討

2. **各タスクに説明を追加**
   - 何を実行するか明確に記述
   - 予想される実行時間や依存関係を明記

3. **タスクリストの表示**
   - TaskList で現在のタスク一覧を表示
   - 進捗状況を可視化

### タスクリスト例

```
1. [ ] 品質チェックの実行（lint, test）
2. [ ] 不要なコメント・デバッグコードの削除
3. [ ] 未コミット状況の確認（git status, git diff）
4. [ ] 変更内容のグループ化
5. [ ] コミットの作成
6. [ ] プロジェクトメモリ更新の検討
```

### エラーハンドリング

- **タスク作成に失敗した場合**: エラーメッセージを表示し、手動で続行するか確認

### 出力

タスクリストが作成され、各ステップの進捗が追跡可能になります。

---

## Step 2: 品質チェック（必須）

### 目的

コミット前にコードの品質を保証します。これは**必須**のステップであり、スキップできません。

### 実行内容

#### 2.1 プロジェクト固有のコマンド確認

以下のファイルを確認して、プロジェクトで定義されている品質チェックコマンドを特定：

- `Makefile`: `make lint`, `make test`, `make format` 等
- `package.json`: `npm run lint`, `npm test` 等
- `pyproject.toml`: `uv run ruff`, `uv run pytest` 等
- `.pre-commit-config.yaml`: pre-commit フックの設定
- `lefthook.yml`: lefthook の設定

---

### 2.1 フォーマット実行

**コマンド**:
```bash
uv run ruff format {対象パス}
# または
make format
```

**目的**: コードスタイルを自動的に統一する

**期待される結果**:
- `5 files reformatted` などの出力
- または `5 files left unchanged`

**注意**: ruff formatは長いログメッセージ（f-string）を自動分割しないため、次のステップでチェックが必要

---

### 2.2 フォーマット検証

**コマンド**:
```bash
uv run ruff format --check {対象パス}
```

**目的**: フォーマットが完全に適用されたことを確認

**期待される結果**:
- `5 files would be left unchanged` （成功）
- または `Would reformat: file.py` （失敗、再度formatが必要）

---

### 2.3 リントチェック（自動修正付き）

**コマンド**:
```bash
uv run ruff check --fix {対象パス}
```

**目的**: 自動修正可能なリントエラーを修正

**期待される結果**:
- `Found 3 errors (3 fixed, 0 remaining)` （修正あり）
- または `All checks passed!` （修正なし）

**修正される例**:
- F401: 未使用のimport
- I001: import順序
- F841: 未使用の変数

---

### 2.4 リントチェック（最終確認）【最重要】

**コマンド**:
```bash
uv run ruff check {対象パス}
```

**目的**: 自動修正できないエラーを検出（特にE501）

**期待される結果**:
- `All checks passed!` （成功）
- または `myproject/use_case/example.py:122:1: E501 Line too long (124 > 120)` （失敗）

**重要**: このステップで`--fix`を付けないことで、E501エラーを確実に検出できます

**E501エラーが出た場合の対応**:

1. エラー詳細を出力：
   ```bash
   uv run ruff check {対象パス} --output-format=full
   ```

2. ユーザーに通知：
   ```
   ❌ 品質チェック失敗: E501（行が長すぎる）

   ファイル: myproject/use_case/example.py
   行番号: 122
   文字数: 124文字（制限: 120文字）

   該当コード:
       f"score ({score} * {score_adjust_rate} = {score * score_adjust_rate}) <= ad_score ({ad_score})"

   修正方法:
   行を分割してください：

   logger.info(
       f"score ({score} * {score_adjust_rate} = {score * score_adjust_rate}) "
       f"<= ad_score ({ad_score})"
   )
   ```

3. 修正を待機してから再度Step 2を実行

---

### 2.5 型チェック

**コマンド**:
```bash
uv run mypy {対象パス}
```

**目的**: 型の整合性を確認

**期待される結果**:
- `Success: no issues found in 15 source files`

---

### 2.6 テスト実行

**コマンド**:
```bash
pytest {対象パス}
```

**目的**: ユニットテストを実行してロジックの正確性を確認

**期待される結果**:
- `15 passed in 2.3s`

### コマンド実行順序

1. **フォーマット**: コードスタイルを統一
2. **リント**: コード品質をチェック
3. **型チェック**: 型の整合性を確認（該当する場合）
4. **テスト**: 機能が正しく動作することを確認

### エラーハンドリング

#### Linter/Formatter が失敗した場合

1. **エラーメッセージを確認**
   ```
   error: Undefined name `foo`
   src/example.py:10:5: F821
   ```

2. **該当ファイルを修正**
   - Read ツールでファイルを読み取り
   - Edit ツールで修正
   - または手動で修正をユーザーに依頼

3. **再度実行**
   - 修正後、再度 Linter/Formatter を実行
   - パスするまで繰り返す

#### テストが失敗した場合

1. **失敗したテストを確認**
   ```
   FAILED tests/test_auth.py::test_login - AssertionError: ...
   ```

2. **関連性を判断**
   - 今回の変更に関連するテストか？
   - 既存のバグによる失敗か？

3. **対応方針の決定**
   - 関連する変更の場合: コードまたはテストを修正
   - 無関係な場合: ユーザーに通知し、対応を確認

4. **修正後に再実行**

### 品質チェック失敗時の原則

**重要**: 品質チェックが失敗した場合、コミットは作成しません。すべてのチェックがパスするまで修正を繰り返します。

### 出力

すべての品質チェックがパスし、コミット可能な状態になります。

---

## Step 3: 未コミット状況確認

### 目的

変更されたファイルと変更内容を詳細に把握します。

### 実行内容

#### 3.1 変更されたファイルのリスト確認

```bash
git status {対象ディレクトリ}
```

**出力例**:
```
On branch feature/auth
Changes not staged for commit:
  modified:   src/auth/login.py
  modified:   src/auth/token.py
  modified:   tests/test_auth.py

Untracked files:
  src/auth/utils.py
```

**確認ポイント**:
- 変更されたファイルの数
- 新規ファイルの有無
- 削除されたファイルの有無

#### 3.2 変更の統計情報確認

```bash
git diff {対象ディレクトリ} --stat
```

**出力例**:
```
 src/auth/login.py     | 15 +++++++++------
 src/auth/token.py     | 23 +++++++++++++++++++++++
 src/auth/utils.py     | 10 ++++++++++
 tests/test_auth.py    |  8 ++++++++
 4 files changed, 50 insertions(+), 6 deletions(-)
```

**確認ポイント**:
- 各ファイルの変更量（追加/削除行数）
- 変更の規模感

#### 3.3 具体的な変更内容の分析

```bash
git diff {対象ディレクトリ}
```

**出力例**:
```diff
diff --git a/src/auth/login.py b/src/auth/login.py
index 1234567..abcdefg 100644
--- a/src/auth/login.py
+++ b/src/auth/login.py
@@ -10,7 +10,8 @@ def login(username, password):
-    token = create_token(user)
+    token = create_token(user, expires_in=3600)
+    validate_token(token)
     return token
```

**確認ポイント**:
- 何が変更されたか（関数、クラス、変数等）
- 変更の目的（機能追加、バグ修正、リファクタリング等）
- 変更の影響範囲

### 分析手順

1. **Read ツールで変更ファイルを読み取り**
   - 変更前後のコンテキストを理解
   - 変更の意図を把握

2. **変更の分類**
   - 各ファイルの変更を以下のカテゴリに分類:
     - 機能追加
     - バグ修正
     - リファクタリング
     - テスト追加
     - ドキュメント更新
     - スタイル修正
     - その他

3. **関連性の判断**
   - どのファイルが互いに関連しているか
   - 同じコミットにまとめるべきか、分割すべきか

### エラーハンドリング

- **変更がない場合**: ユーザーに通知し、終了
- **変更が多すぎる場合**: 複数のコミットに分割することを提案
- **Diff が取得できない場合**: パスやリポジトリの状態を確認

### 出力

変更内容の詳細な分析結果が得られ、次のステップでグループ化に利用されます。

---

## Step 4: 変更内容のグループ化

### 目的

変更を論理的にグループ化し、適切な粒度でコミットを作成する準備をします。

### 実行内容

#### 4.1 変更の分類

Step 3 で分析した変更を以下のカテゴリに分類：

| カテゴリ | タイプ | 説明 | 例 |
|---------|-------|------|-----|
| 機能追加 | `feat` | 新しい機能の追加 | ユーザー認証の追加 |
| バグ修正 | `fix` | バグの修正 | トークン有効期限の修正 |
| リファクタリング | `refactor` | 動作を変えない内部改善 | ユーティリティ関数の整理 |
| テスト | `test` | テストの追加・修正 | 認証テストの追加 |
| ドキュメント | `docs` | ドキュメントの更新 | API ドキュメントの更新 |
| スタイル | `style` | フォーマット、空白等 | インデント修正 |
| その他 | `chore` | ビルド設定、依存関係等 | 開発環境設定の更新 |

#### 4.2 グループの作成

関連するファイルをグループ化：

**グループ化の原則**:
- 同じ機能に関連する変更は同じグループ
- 独立した変更は別のグループ
- 1グループ = 1コミット

**例**:

```
グループ1: feat(auth) - ユーザー認証の追加
  - src/auth/login.py
  - src/auth/token.py
  - src/auth/utils.py

グループ2: test(auth) - 認証テストの追加
  - tests/test_auth.py

グループ3: docs(api) - API ドキュメントの更新
  - docs/api.md
```

#### 4.3 不要なコード・コメントの削除

コミット前に以下を削除：

- **デバッグコード**
  ```python
  # print(f"Debug: {variable}")  # 削除
  # import pdb; pdb.set_trace()  # 削除
  ```

- **不要なコメント**
  ```python
  # TODO: fix this later  # 削除または課題管理システムに移行
  # old implementation  # 削除
  ```

- **未使用のインポート**
  ```python
  # from typing import Dict  # 削除（未使用の場合）
  ```

#### 4.4 グループの優先順位付け

コミットの順序を決定：

1. **依存関係のある変更**: 先にコミット
2. **機能追加**: 次にコミット
3. **テスト**: 機能追加の後
4. **ドキュメント**: 最後
5. **スタイル修正・リファクタリング**: 独立している場合は任意の順序

### 判断基準

#### 同じコミットにまとめるべき変更

- 同じ機能に直接関連する変更
- 一緒にレビューされるべき変更
- 依存関係がある変更

#### 別のコミットに分割すべき変更

- 異なる機能の変更
- 独立してレビューできる変更
- 異なる目的（機能追加とバグ修正等）

### 例：グループ化の実例

#### 変更内容

```
modified: src/auth/login.py      (機能追加)
modified: src/auth/token.py      (機能追加)
added:    src/auth/utils.py      (機能追加)
modified: src/api/endpoints.py   (バグ修正)
modified: tests/test_auth.py     (テスト追加)
modified: tests/test_api.py      (テスト追加)
modified: docs/api.md            (ドキュメント更新)
```

#### グループ化結果

```
グループ1: feat(auth): add user authentication
  - src/auth/login.py
  - src/auth/token.py
  - src/auth/utils.py

グループ2: fix(api): fix response header issue
  - src/api/endpoints.py

グループ3: test(auth): add unit tests for authentication
  - tests/test_auth.py

グループ4: test(api): add tests for API endpoint
  - tests/test_api.py

グループ5: docs(api): update API documentation
  - docs/api.md
```

### エラーハンドリング

- **グループ化が困難な場合**: ユーザーに確認し、意図を聞く
- **変更が多すぎる場合**: 複数回に分けて実行することを提案
- **依存関係が不明な場合**: ユーザーに確認

### 出力

論理的にグループ化された変更のリストが作成され、次のステップでユーザーレビューに進みます。

---

## Step 5: コミット内容のレビュー

### 目的

コミットを実際に作成する前に、各コミットの内容をユーザーに提示してレビューと承認を受けます。

### 実行内容

#### 5.1 品質チェック結果の表示

コミット内容を提示する前に、Step 2 で実行した品質チェックの結果をまとめて表示します。

**表示する情報**:

1. **実行したチェックの一覧**:
   - Linter/Formatter (例: `uv run ruff format`, `make lint`)
   - 型チェック (例: `uv run ruff check`)
   - テスト実行 (例: `pytest`, `make test`)
   - その他プロジェクト固有のチェック

2. **各チェックの結果**:
   - ✅ **Pass**: チェックが成功
   - ❌ **Fail**: チェックが失敗（この場合、コミットは作成されない）

3. **実行コマンド**: 実際に実行したコマンドを表示

4. **サマリー**: すべてのチェックが通過したことを明示

**表示フォーマット例**:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔍 品質チェック結果
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ Linter/Formatter
   コマンド: uv run ruff format .
   結果: すべてのファイルがフォーマット済み

✅ 型チェック
   コマンド: uv run ruff check .
   結果: エラーなし

✅ テスト実行
   コマンド: pytest
   結果: 15 passed in 2.3s

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
✅ すべての品質チェックが通過しました
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**品質チェックが失敗した場合**:

品質チェックが失敗している場合は、この時点でレビューを中止し、エラーを修正してから再度実行します。

#### 5.2 各コミットの内容を提示

Step 4 でグループ化された各コミットについて、以下の情報を明確に提示：

**提示する情報**:

1. **コミット番号**: `コミット 1/3`
2. **コミットメッセージ（案）**: `feat(auth): add user authentication`
3. **含まれるファイル一覧**:
   ```
   - src/auth/login.py
   - src/auth/token.py
   - src/auth/utils.py
   ```
4. **変更の概要**:
   ```
   - 追加: 85 行
   - 削除: 12 行
   - 合計: 3 ファイル変更
   ```
5. **主な変更内容**（オプション）:
   - 新しく追加された関数やクラス
   - 修正された機能
   - 削除されたコード

#### 5.3 提示フォーマット

各コミットを以下のような見やすい形式で表示：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📦 コミット 1/3
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

コミットメッセージ:
  feat(auth): add user authentication

含まれるファイル:
  ✓ src/auth/login.py
  ✓ src/auth/token.py
  ✓ src/auth/utils.py

変更の概要:
  追加: 85 行
  削除: 12 行
  合計: 3 ファイル変更

主な変更:
  - LoginManager クラスを追加
  - JWT トークン生成機能を追加
  - トークン検証ユーティリティを追加

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

#### 5.4 ユーザーへの確認

各コミット（または全コミット）の内容を提示した後、ユーザーに確認を求めます：

**確認方法**:

- すべてのコミット内容を一度に表示してから、全体の承認を求める（推奨）
- または、1つずつ表示して個別に承認を求める

**ユーザーへの質問例**:
```
上記のコミット内容で問題ありませんか？

- 問題なければ「OK」「承認」「proceed」などと返答してください
- 修正が必要な場合は、修正内容を指示してください
  例: "コミット1のメッセージを 'feat(auth): implement user login' に変更"
  例: "utils.py はコミット2に含めて"
```

#### 5.5 修正対応

ユーザーから修正要求があった場合：

**修正可能な項目**:

1. **コミットメッセージの変更**
   - type の変更（feat → fix など）
   - scope の変更
   - subject の変更

2. **ファイルのグループ再編成**
   - ファイルを別のコミットに移動
   - 新しいコミットを作成
   - コミットを分割または統合

3. **コミットの順序変更**
   - 依存関係に基づいて順序を調整

**修正後の再提示**:
- 修正を反映した内容を再度提示
- 再度ユーザーの承認を求める

#### 5.6 承認の確認

ユーザーが以下のような肯定的な返答をした場合、承認とみなします：

- 「OK」「ok」「okay」
- 「承認」「approve」
- 「問題なし」「問題ない」「大丈夫」
- 「proceed」「continue」「go ahead」
- 「yes」「はい」

#### 5.7 コミット前の最終確認

すべてのコミットが承認されたら、次のステップ（コミット作成）に進みます。

### コマンド例

このステップではコマンド実行は不要です。情報の提示とユーザーとのコミュニケーションのみを行います。

### エラーハンドリング

#### ユーザーが拒否した場合

- 理由を確認
- 必要な修正を行う
- 修正後に再度レビューを実施

#### 不明確な返答の場合

- 明確化を求める
- 具体的な修正内容を確認

#### 大量のコミットがある場合

- サマリー形式で表示することを提案
- ユーザーが詳細を見たいコミットだけ詳しく表示

### 出力

ユーザーの承認を得たコミットのリストが確定し、次のステップで実際にコミットが作成されます。

## Step 6: 適切な粒度でコミット

### 目的

ユーザーの承認を得た後、各グループごとに適切なコミットメッセージとともにコミットを作成します。

### 実行内容

#### 6.1 各グループのコミット作成

ユーザーが承認したコミットについて、グループごとに以下を実行：

1. **ファイルのステージング**
   ```bash
   git add <ファイル1> <ファイル2> ...
   ```

2. **コミットメッセージの作成**
   - Conventional Commits 形式に従う
   - 1行かつ英語で記述
   - 変更の内容を明確に説明

3. **コミットの作成**
   ```bash
   git commit -m "<type>(<scope>): <subject>"
   ```

#### 6.2 コミットメッセージの作成ルール

**形式**:
```
<type>(<scope>): <subject>
```

**例**:
```
feat(auth): add user authentication
fix(api): fix response header issue
refactor(utils): organize common utility functions
test: add unit tests for authentication
docs: update API documentation
chore: update development environment config
```

**ルール**:
- **type**: 変更のカテゴリ（feat, fix, refactor, test, docs, style, chore）
- **scope**: 影響範囲（省略可、例: auth, api, utils）
- **subject**: 変更の簡潔な説明
  - 現在形の動詞で始める（"add" not "added"）
  - 小文字で始める
  - 末尾にピリオドを付けない
  - 50文字以内を目安にする

#### 6.3 コミット作成の実例

**例1: 機能追加**

```bash
git add src/auth/login.py src/auth/token.py src/auth/utils.py
git commit -m "feat(auth): add user authentication"
```

**例2: バグ修正**

```bash
git add src/api/endpoints.py
git commit -m "fix(api): fix response header issue"
```

**例3: リファクタリング**

```bash
git add src/utils/helpers.py src/utils/formatters.py
git commit -m "refactor(utils): organize common utility functions"
```

**例4: テスト追加**

```bash
git add tests/test_auth.py
git commit -m "test: add unit tests for authentication"
```

**例5: ドキュメント更新**

```bash
git add docs/api.md
git commit -m "docs: update API documentation"
```

**例6: 設定変更**

```bash
git add .env.example pyproject.toml
git commit -m "chore: update development environment config"
```

#### 6.4 コミット作成時の注意点

**1コミット = 1つの論理的変更**:
- 複数の無関係な変更を同じコミットに含めない
- 1つの変更は1つのコミットにまとめる

**コミットメッセージの品質**:
- 変更の「何」ではなく「なぜ」を説明（必要に応じて）
- レビュアーが理解しやすい表現を使用
- 簡潔かつ明確に記述

**ステージングの確認**:
- `git status` で正しいファイルがステージングされているか確認
- 意図しないファイルが含まれていないか確認

#### 6.5 HEREDOC を使用したコミットメッセージ

フォーマットを保証するため、HEREDOC を使用してコミットメッセージを作成：

```bash
git commit -m "$(cat <<'EOF'
feat(auth): add user authentication
EOF
)"
```

### エラーハンドリング

#### コミット失敗時

1. **エラーメッセージを確認**
   ```
   error: pathspec 'file.py' did not match any file(s) known to git
   ```

2. **原因を特定**
   - ファイルパスが正しいか確認
   - ファイルが存在するか確認
   - Git リポジトリに含まれているか確認

3. **修正して再試行**

#### Pre-commit フック失敗時

1. **フックのエラーを確認**
   ```
   pre-commit hook failed:
   ruff check failed
   ```

2. **問題を修正**
   - 該当ファイルを修正
   - 品質チェックを再実行

3. **新しいコミットを作成**
   - `--amend` は使用しない（前のコミットを変更してしまうため）
   - 新しいコミットとして作成

### 出力

各グループごとにコミットが作成され、Git 履歴に反映されます。

## Step 7: 品質確保

### 目的

コミット後の状態を確認し、すべてが正常に完了したことを保証します。

### 実行内容

#### 7.1 Lefthook プレコミットフックの確認

プロジェクトに Lefthook が設定されている場合、プレコミットフックが正常に実行されたことを確認：

**確認方法**:
```bash
# Lefthook の設定確認
cat lefthook.yml

# または
cat .lefthook.yml
```

**Lefthook フックの例**:
```yaml
pre-commit:
  commands:
    lint:
      run: uv run ruff check .
    format:
      run: uv run ruff format --check .
    test:
      run: uv run pytest
```

**確認ポイント**:
- フックが正常に実行されたか
- すべてのチェックがパスしたか
- エラーや警告がないか

#### 7.2 コミットメッセージの検証

コミットメッセージが正しい形式になっているか確認：

```bash
# 最新のコミットメッセージを確認
git log -1 --pretty=format:"%s"
```

**確認ポイント**:
- Conventional Commits 形式に準拠しているか
- 1行で記述されているか
- 英語で記述されているか
- タイポがないか

#### 7.3 最終的な Git 状態確認

すべてのコミットが完了し、作業ディレクトリがクリーンな状態になっているか確認：

```bash
git status {対象ディレクトリ}
```

**期待される出力**:
```
On branch feature/auth
nothing to commit, working tree clean
```

または、意図的に残したファイルがある場合：
```
On branch feature/auth
Untracked files:
  .ai_workspace/   (これは意図的)
```

**確認ポイント**:
- すべての変更がコミットされたか
- 意図しないファイルが残っていないか
- ブランチが正しいか

#### 7.4 コミット履歴の確認

作成されたコミットを確認：

```bash
# 最新のN個のコミットを表示
git log -n 5 --oneline

# または詳細表示
git log -n 5 --pretty=format:"%h - %s (%an, %ar)"
```

**確認ポイント**:
- 期待通りのコミットが作成されたか
- コミット順序が正しいか
- コミットメッセージが適切か

#### 7.5 Diff の最終確認

各コミットの変更内容を確認：

```bash
# 最新のコミットの変更内容
git show HEAD

# 特定のコミットの変更内容
git show <commit-hash>
```

**確認ポイント**:
- 意図した変更のみが含まれているか
- 不要なファイルが含まれていないか
- デバッグコードが残っていないか

### エラーハンドリング

#### Lefthook が失敗した場合

1. **エラーメッセージを確認**
2. **問題を特定**（lint、test、format 等）
3. **修正**
4. **再度コミット**（新しいコミットとして作成）

#### 作業ディレクトリがクリーンでない場合

1. **残っているファイルを確認**
   ```bash
   git status
   ```

2. **意図的なものか判断**
   - `.ai_workspace/`: 通常は意図的
   - その他: 追加のコミットが必要か確認

3. **必要に応じて追加のコミットを作成**

### 出力

すべてのコミットが正常に作成され、品質が保証された状態になります。

## Step 8: プロジェクトメモリ更新検討

### 目的

作業中に発見した技術的課題や解決方法を記録し、将来の開発効率化につなげます。

### 実行内容

#### 8.1 作業中に得た知見の特定

以下のような知見がある場合、記録を検討：

- **新しいエラーパターン**
  - 遭遇したエラーとその解決方法
  - 例: "ruff のバージョンXでYのエラーが発生 → Zで解決"

- **ライブラリ使用方法**
  - 新しいライブラリの使い方
  - ハマりポイントと回避方法
  - 例: "pytest-asyncio は pytest.ini に設定が必要"

- **設定の注意点**
  - プロジェクト固有の設定
  - 環境構築時の注意点
  - 例: ".env.example の DATABASE_URL は必須"

- **パフォーマンス改善**
  - ボトルネックとその対策
  - 例: "N+1問題をeager loadで解決"

- **ベストプラクティス**
  - プロジェクトで採用すべきパターン
  - 例: "認証トークンは常にexpires_inを指定"

#### 8.2 CLAUDE.md への追加検討

プロジェクトの CLAUDE.md ファイルに知見を追加するか検討：

**追加すべき内容**:
- 繰り返し遭遇する可能性が高い問題
- プロジェクト固有の重要な知識
- 開発効率化につながる情報
- セキュリティやパフォーマンスに関する重要な知見

**追加すべきでない内容**:
- 一時的な問題
- 個別のバグ修正の詳細
- 既にドキュメント化されている内容
- プロジェクト外でも一般的に知られている内容

#### 8.3 CLAUDE.md の更新

必要に応じて CLAUDE.md を更新：

1. **Read ツールで CLAUDE.md を読み取り**
   ```
   Read CLAUDE.md
   ```

2. **適切なセクションを特定**
   - 既存のセクションに追加するか
   - 新しいセクションを作成するか

3. **Edit ツールで追加**
   - 簡潔かつ明確に記述
   - 具体例を含める
   - 関連する情報へのリンク

**例**:

```markdown
## 開発環境

### 品質チェック

プロジェクトでは以下のコマンドで品質チェックを実行：

```bash
make lint    # ruff format + ruff check
make test    # pytest
```

**注意**: pytest-asyncio を使用する場合、pytest.ini に以下を追加：

```ini
[pytest]
asyncio_mode = auto
```
```

#### 8.4 lessons.md への記録（CLAUDE.md の指示に従う）

CLAUDE.md の "Self-Improvement Loop" セクションに従い、ユーザーから修正を受けた場合は `.ai_workspace/claude/lessons.md` に記録：

**記録すべき内容**:
- ミスしたパターン
- 正しいアプローチ
- 今後の改善ポイント

**例**:

```markdown
## 2026-03-02: コミットメッセージの形式ミス

### 問題
コミットメッセージを日本語で作成してしまった。

### 正しいアプローチ
Conventional Commits 形式で必ず英語を使用する。

### 改善ポイント
コミット作成前にメッセージ形式を再確認する。
```

### エラーハンドリング

- **CLAUDE.md が存在しない場合**: 新規作成するか確認
- **セクションが不明な場合**: ユーザーに確認

### 出力

プロジェクトメモリが更新され、将来の開発がスムーズになります。

## まとめ

Smart Commit の8ステップワークフローは以下の流れで実行されます：

0. **対象ディレクトリの取得**: コミット対象を特定
1. **作業計画の作成**: タスクリストで進捗を可視化
2. **品質チェック**: lint、test を実行してコード品質を保証
3. **未コミット状況確認**: 変更内容を詳細に分析
4. **変更内容のグループ化**: 論理的にグループ化
5. **コミット内容のレビュー**: ユーザーにコミット内容を提示して承認を得る
6. **適切な粒度でコミット**: Conventional Commits 形式でコミット作成
7. **品質確保**: Lefthook 確認、最終状態確認
8. **プロジェクトメモリ更新検討**: 知見を記録

各ステップを丁寧に実行することで、高品質なコミットが作成されます。
