# ore-task — タスク台帳の定期更新

Notion 上のタスク台帳を**まとめて棚卸しして最新化する**ときに使う。

単発の操作はこのスキルの対象外。「これタスクにして」「〇〇-12 終わった」は
`docs/task-system/public.md` §5 に従って会話でそのまま処理する。

---

## 前提（起動時に即実行・スキップ禁止）

1. `~/.ai_agent/docs/task-system/public.md` を読む
2. 同ディレクトリの `private.md` を読む（**記述が競合したら private 側を優先**）
3. 対象 DB は private 側 §1 に記載の id で指定する。**`notion-search` で DB を探さない**（旧 DB に誤って書く事故が起きる）
4. private 側が無い、または id が未記入なら**作業を止めて確認する**

> **運用ルールの本体は `docs/task-system/` にある。このスキルは順序・関門・部分実行の制御だけを持つ。**
> ルールを変えたいときは docs 側を直す。このファイルに複製しない（二重管理になった時点で価値が消える）。

---

## 回す順序

| # | ステップ | 書き込み | 人を待たせるか |
|---|---|---|---|
| 1 | 棚卸し（確認対象の洗い出し） | なし | いいえ |
| 2 | 進捗の調査 | なし | いいえ |
| 3 | 起票候補の抽出 | なし | いいえ |
| 4 | 順位案の作成 | なし | いいえ |
| 5 | **変更案の提示 → `y/n` → 書き込み** | あり | **ここだけ** |

### 関門は1つだけ

**ステップ1〜4は読み取りのみで最後まで走り切る。途中で承認を求めない。**
**ステップ5で全ての変更を1枚にまとめ、`y/n` を1回だけ取る。**

なぜ1つにするか。

- ステップごとに承認を取ると、**調査待ちのたびに人が画面に張り付く**ことになる。
  調査は Slack / GitHub の往復で分単位かかり、その間ずっと待たせる
- **起票は順位に影響する。** 別々に承認を取ると、起票の承認→順位の提示→順位の承認と、
  同じ話を2回見せることになる
- 途中に関門があると、人は**判断より先に「進めていいか」を答えさせられる**。
  読み取りに承認は要らない（`instructions/core.md`「読み取り専用の操作は承認不要」）

### 途中経過は「報告」であって「確認」ではない

ステップ1〜4で人に見せるのは**1〜2行の進捗だけ**。表を出さない。

```
未完了 20件を取得。確認手段を紐づけた15件を調査します（5件は手段が無いのでスキップ）。
GitHub 5件 / Slack 4件 / Notion 3件 / ローカル 2件 に分けて並列で確認します。
```

**表はステップ5にしか出さない。** 途中で表を出すと、人は「これに答えるべきか」と迷う。

## ステップ1: 棚卸し（確認対象の洗い出し）

未完了（`Todo` / `Doing` / `Waiting`）を**全件**取得し、各タスクに
**「何を見れば状態が決まるか」** を紐づける。

プロパティだけでなく**本文も読む**。待ち先とリンクは本文にしかない。

### 紐づけの型

| 台帳の状態 | 何を見るか | 何が分かるか |
|---|---|---|
| `Waiting` | 本文の「誰の何待ち」→ 該当する Slack スレッド | 返答が来ていれば `Doing` へ戻す |
| 本文に PR リンク | PR の `state` / マージ時刻 / 自分の review | `MERGED` かつ自分が `APPROVED` なら `Done`。他者が対応していれば `Dropped` |
| 本文に Notion / Figma リンク | そのページの更新・コメント | レビューが済んでいるか |
| 本文にローカルのパス・リポジトリ名 | そのファイル・ブランチの現状 | 自分または他者が既に着手したか |
| `Doing` のまま動きが無い | 直近の自分の作業・発言 | 実態が `Waiting` か、放置か |
| `Due` が超過・接近 | （見に行かない） | ステップ4で先頭へ寄せる |
| 確認手段が無い | **見に行かない** | ステップ5で「変更なし」に入れる |

**この時点で表を出さない。** 件数と、これから何を見るかを1〜2行で報告して次へ進む。

---

## ステップ2: 進捗の調査

**ステップ1で挙げた対象だけを見に行く。台帳全体を漁らない。**

### 調査はサブエージェントに委譲する

確認対象が確定しているので委譲できる。メインのコンテキストを守るため委譲する。

- **委譲の単位は確認手段の種類ごと**（GitHub 系で1つ、Slack 系で1つ）。並列で投げる
- 返させるのは **「タスク / 見たもの / 一次情報 / 状態の判定」だけ**。生ログを返させない
- **委譲先に「書き込み禁止」を明示する**（PR コメント・Slack 投稿・下書き作成をさせない）
- **Notion の追加取得とローカルのファイル確認はメインでやる**。安く済むものを委譲すると往復が増える
- **書き込みは委譲しない。** ステップ5でメインが行う

### 判定の質

- **根拠は一次情報で持つ** — PR の `state` / マージ時刻 / Slack の発言と時刻。「〜のはず」を通さない
- **判断が弱いものは弱いまま持ち上げる**（review が `COMMENTED` のときの `Waiting` / `Doing` など）。
  丸めて確定させない

---

## ステップ3: 起票候補の抽出

手順は `public.md` §5「Slack の保存済みから起票」に従う。ここでは制御だけ定める。

- 期間は **`after:` で直近2週間**。間隔が空いていてもそれ以上は遡らない
- **突合用の既存タスクは `Source` が入っているもの全件。** ステップ1で取った未完了だけでは足りない
  （`Done` / `Dropped` でヒットしたら処理済み・見送り済み）
- 検索と仕分けの調査はサブエージェントに委譲してよい。**判定結果だけ返させる**
- **同テーマの既存タスクがあれば新規起票せず本文に追記する**（タスク名でも見比べる）

### 順位は仮置きでよい

`public.md` §5 には「運用の一次対応 / 期限が迫る / レビュー依頼なら割り込ませる」とあるが、
**ステップ4で全体を振り直すため、ここでは末尾 +10 の仮置きで持つ。**
割り込みの承認を二重に取らない。

---

## ステップ4: 順位案の作成

未完了（**ステップ3の起票候補を含む**）を種類順に並べ、10刻みで振り直す。

1. 運用からの問い合わせの一次対応
2. 期限が迫っているもの
3. レビュー依頼
4. プロダクトバックログ開発
5. その他

- 同じ種類の中は `期限` → **起票日（`createdTime`）が古い順** → 軽さ で並べる
- **古さは軽さより優先する。** 「軽いから先に」で新しいものを上げない
- 同じ種類・同じ起票日なら `Doing` を先に置く
- **`Waiting` は種類の位置を保ったまま、同種内では末尾**
- **依頼者の稼働状況（不在など）で並べ替えない。** 言われたときだけその場で反映する

---

## ステップ5: 変更案の提示（唯一の関門）

**ここで初めて表を出す。** 冒頭に**聞きたいことの件数**を書く。

```markdown
## 変更案

**判断が必要なのは 2 件です。** 下の A だけ答えてください。
`y` と返せば全て推奨どおりに書き込みます。

### A. 判断が必要（2件）
### B. そのまま書き込む（5件）
### C. 変更なし（19件）
### D. 順位の振り直し（20件）

回答例: `y` / `1b` / `1b, 2a`
```

### A. 判断が必要

**先頭に置く。1件ずつ、番号 → 選択肢（英字）→ 推奨1つ → 理由1行。**

```markdown
1. **{ID prefix}-41 社内推薦文の提出 —— `Done` にするか**
   a. `Done` にする（推奨）—— 8/14 18:54 に本人が提出報告。本文の残作業が消えた
   b. `Doing` のまま —— 相手の受領返信を待つ
```

- **`ID` 単独で示さない。必ず `Name` を併記する。** ID だけでは何の話か判断できない
- **推奨を必ず1つ置く。** 選択肢を並べるだけでは判断を丸投げしたことになる
- 判断が弱い理由（一次情報が足りない・解釈が割れる）があれば1行で書く
- **ここが0件なら「判断が必要なものはありません」と明示する。** 空の見出しを置かない

### B. そのまま書き込む

`public.md` §5 の形式。**1プロパティ1行。**

| ID | Name | 項目 | Before | After | 根拠 |
|---|---|---|---|---|---|

- **根拠は一次情報で書く** —— PR の `state` / マージ時刻 / Slack の発言と時刻
- **`Done` / `Dropped` へ変えるときは `役割` も行に入れる。**
  「PR の author は他者・自分は APPROVED だけ」→ `レビュー`、
  「自分が原因特定し修正は他者がリリース」→ タスク名の成果物が調査なら `主担当`。
  **迷ったら A へ回す**（振り返りの集計が変わるため、勝手に決めない）

### C. 変更なし

**表にしない。ID と Name を1行に羅列する。**

```markdown
{ID prefix}-3 媒体Aの生成前スキップ / {ID prefix}-36 <repo>#953 のレビュー / …（計19件）
うち確認手段が無くスキップ: 5件（{ID prefix}-7 / -10 / -11 / -22 / -40）
```

表で全件出すと、**A の1件が19行の中に埋もれる。** これを避けるための区分なので、
ここを厚くしたら区分の意味が消える。

**一次情報を見たうえで「変わらない」と判断した根拠は、完了報告に回す。** ここには書かない。

### D. 順位の振り直し

**4列だけ。** 順位 / ID / Name / 種類。

| 新順位 | ID | Name | 種類 |
|---|---|---|---|

**なぜその順かは、表の下に種類ごと1行でまとめる。**

```markdown
- 種類2（期限が迫る）: 2件。Due の近い順（8/18 → 8/31）
- 種類3（レビュー依頼）: 起票日の古い順。8/12 の4件は同日なので軽い順（最軽量が1ファイル、最重量が30ファイル）
- 種類5（その他）: 起票日の古い順。8/6 の8件は同日なので Doing を先に、あとは軽い順
```

各行に理由を書くと20行×6列になり、**読むべき点（この並びでよいか）が埋もれる。**

- **全件を順位つきで出す**（上位N件に絞らない）
- 期限超過・長く動いていないものは**完了報告**で知らせる。ここには混ぜない

## 書き込み（ステップ5の承認後）

- **書き込みの直前に対象を再取得し、提示時との差分を確認する。**
  人が Notion UI で触っていることがあり、セッション中に `Status` が変わる・
  タスクが未完了リストから消える。
  - **提示した変更と方向が違う差分**（承認と逆の変更・想定外の Status）→ **書き込みを止めて報告する**
  - **提示した変更が既に人の手で入っている**（同じ方向）→ **未適用の分だけ書き込み、完了報告で知らせる**
- **`Status` を変えたら本文に1行追記する** — `- YYYY-MM-DD <内容>` を `insert_content`（`position: end`）で
- **`Waiting` は誰の何待ちかを必ず書く**
- `Done` / `Dropped` にしたら `完了日` を埋めて `順位` を空にする
- **`Done` / `Dropped` にしたら `役割` も埋める** — `主担当` / `レビュー` / `関与のみ`（`public.md` §2）
- **他者が対応して完了したものは `役割` で区別する**（`public.md` §5）。
  自分の寄与があれば `Done` + `関与のみ`、何も寄与せず決着したなら `Dropped`
- 順位は**変わったものだけ**書く（Notion に一括更新 API はない）

## 部分実行

| 言われ方 | 回すステップ | ステップ5で出す区分 |
|---|---|---|
| 「棚卸しして」「台帳を更新して」（**デフォルト**） | 1 → 2 → 3 → 4 → 5 | A / B / C / D |
| 「同期だけ」「ステータスを更新して」 | 1 → 2 → 5 | A / B / C |
| 「起票だけ」「slack の後でを見て起票して」 | 3 → 5 | A / B（終了時に順位整理を提案する） |
| 「順位整理して」「今の状況は？」 | 1（確認手段の紐づけは省く） → 4 → 5 | D |

**ステップ2の前には必ずステップ1を通す。** 単独で走らせない。
**どの入り方でも関門は1回。**

---

## 完了報告

- 起票 N 件 / 更新 N 件 / 順位を振り直した N 件
- **次にやる上位3件**（ID・**`Name`**・なぜ先頭か）
- 期限超過・長く放置されているもの（あれば）
- **提示時から台帳が動いていたもの**（人が UI で触った形跡。あれば）
- **判断が弱いまま残したもの**（一次情報では決まらなかったもの。あれば）
- 確認手段が無くスキップしたものを1行

## 育て方

**このスキルには運用ルールを足さない。** 困ったことが出たら `docs/task-system/public.md` §6 に足す。
このファイルを変えるのは、**回す順序・関門の位置・提示の形・部分実行の対応表**が実態と合わなくなったときだけ。

### 改訂の記録

- **v2.0.0（2026-08-14）** —— 関門を3つ（同期 / 起票 / 順位）から**1つ**に集約した。
  実運用で `y/n` が3回発生し、その都度サブエージェントの調査待ちを人が待つ形になっていた。
  併せて提示の形を規定 —— 途中経過は1〜2行の報告のみ・表はステップ5だけ・
  変更なしは羅列1行・順位表は4列。**判断が必要な1件が「変更なし19件」の表に埋もれた**ため。
- **v2.1.0（2026-08-14）** —— 同種内の並びを「起票日が古い順」優先に変更した（`public.md` §5 の改訂に追随）。
  依頼者の稼働状況で並べ替える記述を削除した。
