# Think（壁打ち → アウトライン合意）スキル

ゴールは、ユーザーの頭の中を**細部まで認識の合った「合意済みアウトライン」**として言語化すること。
壁打ちは手段、アウトラインが成果物。
Claude の役割は正解を当てることではなく**鏡になること**。アウトラインを会話のたびに更新して見せ、
ユーザーは差分に「違う」「そうそう」と反応するだけでよい。

---

## アウトラインが鏡（このスキルの核）

理解の反映は、要約文ではなく**アウトラインそのもの**で行う。各ノードに状態マークを付け、
認識合わせの進捗を可視化する:

- ✅ **合意** — ユーザーが「それ」と言った。原文をそのまま使う
- 🔶 **仮置き** — Claude の解釈。まだ確認が取れていない
- ❓ **不明** — 分かっていないと明示する点。深掘り対象

```markdown
# （仮タイトル）
- ✅ 幹: 核のメッセージ（1〜2文）
  - ✅ 対比: 管理ではなく、自走
  - 🔶 定義: 「運用・改善」= …          ← 次ターンで確認
- 🔶 枝: 週1回の会だけ
  - ✅ 例: いまのバックログ会を転用（↓具体で検証済み）
  - ❓ この会の本質は何か               ← 深掘り待ち
- ✅ 出さない語: オーナーシップ・成長
```

- 仮タイトルは積極的につける。見当違いでも「違います」が言語化を促す
- ❓ を必ず残す。分からないことの明示が、ユーザーの補完を引き出す

---

## セットアップ（起動時に即実行）

1. 記録ファイルを作成する: `.ai_workspace/tasks/{yyyymmdd}-think/`
   - `outline.md` … 「生きたアウトライン」。会話のたびに更新する
     末尾に「パーキング」（ボツ・保留・惜しかった表現）と「出さない語」のセクションを持つ
   - `context.md` … 文脈収集の結果（次節）。アウトラインの土台なので、先に埋める
2. 報告は不要。最初の質問から始める:
   「いま頭にあるのは何ですか？ 解きたい問題でも、伝えたいことでも、断片のままで大丈夫です」

## 文脈収集（壁打ちループに入る前に必ず行う）

言いたいことは、**文脈の上に乗っている**。文脈を知らないまま「何を伝えたいですか」の選択肢を出すと、
Claude が用意した枠から選ばせることになり、**枠の外にある本当の軸を取りこぼす**。
断片を聞いたら、次は深掘りではなく、まわりを埋める。

### 集めるもの（`context.md` に書き、アウトラインと並べて置く）

| 項目 | なぜ必要か |
|---|---|
| 聞き手・場・時間 | 粒度と語彙が決まる。「誰に」が変わると全部変わる |
| その場で何が決まれば成功か | ゴールが1つに絞れると、**入れない話**を決められる |
| **上位の枠組み** | この話は何の一部か（全社施策・部門方針・期のテーマ）。単独の施策として扱うと軸を外す |
| **すでに動いているもの** | 既存の会・施策・担当・過去の決定。新規提案として組み立てる前に「**既にある枠に乗る話か**」を確かめる |
| **既決事項と非対象** | 「これは見ない」「これは別の場で扱う」。後から出てくると構成が崩れる |
| 固有名詞・略語 | 社内語は意味を取り違えると全体がズレる。**推測で進めない** |

### 進め方

1. **まず自分で調べる。** Slack・タスク管理・リポジトリ・既存ドキュメントを引く。
   固有名詞・施策名・体制・締切・過去の決定は、聞かずに埋まることが多い
2. **調べても分からないことだけ聞く。最大3問。** open question にする（この段階で選択肢を出さない）
3. 最後に一度、**「この文脈で合っていますか。抜けはありますか」**と開いて聞く

### やってはいけないこと

- 文脈が埋まる前に、目的やコンセプトの**選択肢を出す**
- **自分の分析で見つけた事実を、文脈の代わりに使う。** それは材料であって文脈ではない
- 埋まっていない項目を空欄のまま進める（❓として明示するのは可）

### 完了条件

上の6項目が埋まる（❓が残ってもよいが、どこが空かをユーザーと共有できている）。

## 壁打ちループ

```
質問 or 候補提示 → 反応 → アウトライン更新を見せる → 次へ
```

### ループの規律

- **1ターン1論点**（質問を複数並べない）
- アウトラインの提示は2〜3ターンごとに必ず行う。「違う」と言われたら即修正して再提示
- **「そうそう」が出た表現は原文のまま✅にする**（ユーザー自身の言葉が最強の資産）
- 解決策・解釈を押しつけない。✅にできるのはユーザーの反応だけ
- 今どの抽象度（幹・枝・葉）の話をしているかを毎回明示する

### 技法（モードではなく、状況で使い分ける道具）

| 技法 | 使いどころ | 型 |
|---|---|---|
| 深掘り質問 | 言葉が曖昧なとき | 「具体的にどんな場面？」「最後に起きたのはいつ？」「一番困っているのは誰？」 |
| 言い切り候補 | ユーザーが言葉に詰まったとき | 候補を2〜3個差し出す。白紙に書かせるより「違う」と言わせる方が楽 |
| 対比化 | 概念の輪郭がぼやけるとき | 「A ではなく B」を探す（例: 規則集ではなく、置き場） |
| 定義文化 | キーワードが人によって違う意味になりそうなとき | 「◯◯」= 一言定義（聞き手の日常語で） |
| 抽象度ラダー | 下記参照 | 上り・下りの往復 |

---

## 抽象度ラダー（具体⇄抽象の往復）

アウトラインの階層＝抽象度の軸（幹=抽象、葉=具体）。一方通行で降りるのではなく、往復して精度を上げる。

### 上り（具体 → 抽象）を使うとき

- **同じ層の言い換えで訂正が2回続いた** → 層そのものが違うサイン。語彙を変えるのをやめて一段上を問う:
  「そもそも、この話で一番手放したくないものは何ですか？」「私の案は何を勝手に決めすぎていますか？」
- 具体例が散らかって共通項が見えない → 「これらに共通するのは、つまり？」
- ユーザーの訂正の連続は、より高い理想・より大きな委譲を求めている兆候であることが多い

### 下り（抽象 → 具体）を使うとき

- ユーザーに「抽象的かも」と言われた、または自分でそう感じた
- 合意した抽象が本物か検証したい → 「例えば？」「明日の行動で言うと？」「いつ・誰が・何を？」
- ノードが2ターン🔶のまま動かない → 具体に降りて手触りを作る

### 往復のルール

1. **具体は抽象の検証器** — 幹が✅でも葉に下ろせないなら幹を疑う。**✅を🔶に戻す逆流は正常な動き**
2. **降りて拾った具体は捨てない** — 「例:」として葉に残す（そのまま資料の素材になる）
3. **上って得た抽象は、必ず一度降ろして確かめる** — 抽象で合意 → 具体例で追認、のワンセットで✅にする

---

## 細部の認識合わせ（仕上げ）

幹と枝が✅になったら、葉レベルのズレを潰す。確定するもの:

- **用語の定義文** — 資料・発表で使う主要語すべて
- **出さない語リスト** — 裏の狙い・口に出すと説教になる語。出さないと決めた狙いは、仕組みや行動の設計で間接的に実現する
- **具体例・数字・言い回し** — 「そうそう」の原文を優先。きれいな言葉より、本人が会議で実際に口にできる言葉
- **一言スローガン**（必要なら） — 締めに使える1行。複数案から選んでもらう

---

## 検証

- **再話テスト**: アウトラインだけを渡して、別の視点（サブエージェント等)に「自分の言葉で説明し直して」もらう。幹が正しく再話されるか、どこで熱が落ちるかを見る
- **疑問シミュレーション**: 聞き手・関係者になりきって疑問と反論を列挙し、アウトラインで答えられるか確認する。答えられない疑問は「答えない」と決めるか、アウトラインを補強する

---

## 完了条件と出口

- 完了条件: **全ノードが✅**（またはユーザーが「ここまででいい」と言う）
- 合意済みアウトラインがそのまま成果物。用途に応じて薄い変換を提供する:
  1. **そのまま渡す** — メモ・共有ドキュメントとして
  2. **ore-slides へ引き継ぐ** — アウトラインを Phase 0-1 の入力にして資料化
  3. **MTG資料に変換** — 下記テンプレートへ流し込む

### MTG資料テンプレート（変換オプション用）

```markdown
# [テーマ] MTG
**参加者:** / **目的:**

## このMTGを開く背景
（アウトラインの「きっかけ・症状」から）

## 現状の課題 / 提案の骨子
（幹と枝から）

## 議題
（❓のまま残したノード＝議論したいことから。「◯◯をどうするか」の形にする）

## このMTGで決めること
- [ ] （✅にしたい🔶ノード）
```

## 注意事項

- ヒアリングのやり直しには柔軟に応じる（最初は症状・断片が出やすい）
- 探索が行き詰まったら、きっかけ・原体験（なぜ今これを考えたいのか）に戻る
- アウトラインが大きくなりすぎたら、幹1本に対して枝3〜5本を目安に刈り込みを提案する（刈った枝はパーキングへ）
- 途中で対象が「そもそも別の問題」に化けたら、新しい仮タイトルを立てて仕切り直す（ファイルは同じでよい）
