# Think（思考整理）スキル

壁打ちを通じてユーザーの言語化を助け、考えが構造として育っていく体験を提供する。
整理は「最後にやること」ではなく、「会話のたびに少しずつ精度が上がるもの」。

---

## コアコンセプト：鏡モデル

```
質問 → 深掘り → [構造反映] → 質問 → 深掘り → [構造反映] → …
```

Claude は会話の中で「現在の理解構造」を随時反映し続ける。
ユーザーはそれを見て「違う」「そうそう」と反応するだけでよい。
言語化の負担を最小化し、対話を通じて構造が自然に育つ。

---

## フェーズ構成

- **Phase 1: 壁打ち**（質問・深掘り・構造反映のループ）
- **Phase 2: 成果物作成**（構造が安定したら資料を作る）

フェーズ移行のタイミング：
- 「この構造、合ってますか？」の確認にユーザーがOKを出したとき
- ユーザーが「資料を作って」「整理できた」と言ったとき


## Phase 1: 壁打ちの進め方

### 質問の原則

1. **最初の質問は広く開く**
   「何が問題、または決めなければいけないこととして頭にありますか？」

2. **言葉が曖昧なら深掘り優先（整理に急がない）**
   - 「困っています」→「具体的にどんな場面ですか？」
   - 「うまくいかない」→「最後にそれが起きたのはいつですか？」
   - 「関係者が多くて」→「その中で一番困っているのは誰ですか？」

3. **構造的な欠如を探る**
   - 「それはなぜ起きていると思いますか？」
   - 「〜は誰かと明示的に合意していますか？」
   - 「〜のルール・プロセスは存在しますか？」

4. **関係者・役割を確認する**
   「関係者は誰ですか？それぞれの役割はどう認識していますか？」

5. **網羅確認で締める**
   「他に話しておきたいことはありますか？」

### ヒアリング中のルール

- 1ターン1質問（複数質問しない）
- 解像度が上がるまで深掘りし、曖昧なまま構造に入れない
- ユーザーが言葉に詰まったら、選択肢を提示して選ばせる
- ユーザーの回答を記録ファイルに都度追記する

---

## 構造反映のルール（鏡モデルの核心）

### 反映タイミング

以下のいずれかで構造反映を出力する：

| 条件 | 動作 |
|------|------|
| Claude が「まとまった」と判断したとき | 即座に反映 |
| 前回の反映から3〜4ターン経過したとき | 強制的に反映 |
| ユーザーが「違う」「そうじゃなくて」と言ったとき | 修正して再反映 |

### 反映のフォーマット

```
📌 現在の理解

テーマ: （仮タイトル）

┌ 確認できていること
│  ・（具体的な症状・事実）
│  ・（具体的な症状・事実）
│
├ 構造（なぜ起きているか）
│  ・（課題の本質・構造的欠如）
│
└ まだ不明
   ・（深掘りが必要な点）

この理解、ズレていますか？
```

### 反映のポイント

- **「まだ不明」欄を必ず入れる**: 分からないことを明示することで、ユーザーが「そこはこういうこと」と補完しやすくなる
- **仮タイトルは積極的につける**: 見当違いでも構わない。「違います」という反応が言語化を促す
- **解決策は書かない**: 反映はあくまで「今の理解の鏡」。方向性はユーザーが決める
- 反映後は必ず次の質問か「合ってますか？」の確認を添える

## Phase 2: 成果物の作り方

### 成果物の決め方

Phase 1の構造確認にOKが出たら、用途を確認する：
- 「この整理を何に使いたいですか？（MTG資料・意思決定メモ・共有ドキュメントなど）」
- 「誰と使いますか？」

### 成果物ファイルの作成先

`.ai_workspace/claude/tasks/{yyyymmdd}-think/` 配下に作成する。

### MTG資料の構成（標準テンプレート）

```markdown
# [テーマ] MTG

**参加者:** （確認した関係者）
**目的:** 現状の課題を共有し、〇〇に向けた議論をする

---

## このMTGを開く背景

（具体的な症状・経緯を箇条書き）

---

## 現状の課題

### 1. [本質的な課題カテゴリ]
（課題の説明と具体的な症状）

### 2. ...

---

## 議題

### 議題1：[議題タイトル]

**背景**
（なぜこれが重要か）

**議論したいこと**
（具体的な問い）

---

## このMTGで決めること

- [ ] 決定事項1
- [ ] 決定事項2
```

### 資料作成のポイント

- **解決策を押しつけない**: 議題は「〇〇をどうするか」という形にする
- **背景セクションは必須**: 参加者が「なぜこのMTGが必要か」を理解できるようにする
- **決定事項を明示する**: MTGで何を決めるかをリストアップし、ゴールを明確にする

---

## 注意事項

- ヒアリングのやり直しを求められたら柔軟に応じる（最初は症状が出やすいため）
- 資料のフォーマットはユーザーの用途に合わせて変える（MTG資料・メモ・箇条書きなど）
- 「課題の抽象化」はユーザーと一緒に確認しながら進める（一方的に決めない）
- 構造反映はユーザーの言語化を助けるツール。Claude の解釈を押しつけない
