## Conversation Guidelines

- **常に日本語で会話する**
- **選択肢を提示する際は必ず番号またはアルファベットを付ける**
  - 通常は番号を使う（例：1. ～, 2. ～）
  - 複数の選択肢グループを同時に表示する場合や、質問内容に数字が含まれて紛らわしい場合はアルファベットを使う（例：a. ～, b. ～）
  - **不可逆な操作（push・履歴書き換え・PR のマージ・復旧不能な上書き）を含む選択は、片方を括弧書きの補足に落とさない。**取り返しのつきやすさを添えて対等に並べる
- **承認・確認を求める際は必ず `y/n` を表示する**。ユーザーが y/n で答えられるようにする
  - **曖昧な返答を承認と解釈しない。**`y/n` を求めたあとに来た別の指示は、承認ではなく新しい指示として扱う（提示した選択肢への番号・記号での回答は承認に含む）
- **実装を始める前に、どこまで進めるかを確認する** — `1. 変更のみ` / `2. コミットまで` / `3. push・PR まで`
  - **合意した範囲は完了後に改めて聞かず、そのまま最後まで進める。** 都度確認しない
  - `3` なら**着手前にブランチを切る**（1ブランチ = 1PR。実装後に main にいたと気づいても戻せない）
  - 合意した範囲を超えるときだけ確認する
- **複数件を一覧で提示するときは、判断が必要なものを分離して先頭に置く**
  - **判断不要のもの・変更なしのものの山に埋もれさせない。** 全部を1つの表に並列で並べると、判断すべき1件が読み飛ばされる
  - **区分の数と名前は、その場面のスキルに規定があればそれに従う**（`ore-task` は4区分、`ore-improve` は2区分など）。規定が無いときだけ自分で決める
  - 各行に対象の**名前**を出す。ID や番号だけで示さない
  - 判断が必要なものは選択肢を記号で並べ、**推奨を1つ示して理由を1行**添える
  - **全件を順序どおり見せることが目的のもの（順位づけ・アウトライン・目次）には適用しない。** 分割すると読めなくなる

## File Creation Guidelines

- **一時的なファイルや結果ファイルの作成場所**
  - テスト用ファイル、実験用ファイル、分析結果をまとめたファイルなど、一時的なファイルを作成する場合は、必ずその時点のプロジェクトルート（Primary working directory）直下の `.ai_workspace/tasks/{yyyymmdd}-{word}/` ディレクトリ以下に作成すること
  - `{yyyymmdd}` は作成日の日付を8桁で表し（例：20260212）、`{word}` は7文字以内のランダムな英単語とする。これにより同日実行時の重複を避ける
  - このルールは、プロジェクトの正式なソースコードファイルには適用されません

- **軽微な一時ファイルの作成場所**
  - タスクに切るほどでもない一時ファイル（ちょっとした検証、スニペット等）は、プロジェクトルート直下の `.ai_workspace/tmp/{yyyymmdd-HHMMSS}/` ディレクトリを作成して配置すること
  - `/tmp` やその他の作業ディレクトリ外への書き出しは禁止。作業ディレクトリ内に閉じること

## Design Document Guidelines

- **設計をマークダウンに書き出すときは、本文より先にアウトラインを出す**
  - 形式は「見出しの一覧＋各見出しの1行要約」。**本文を書く前に提示して合意を取る**
  - 構成のズレは本文を書き切ってからでは直せない。骨組みの段階で合わせる（`ore-think` / `ore-slides` と同じ順序）
- **合意したアウトラインは文書の冒頭にそのまま残す**
  - 読み手が全文を読まずに構成を把握でき、レビューが「差分を追う」から「構造を見る」に変わる
  - 本文の構成を変えたらアウトラインも直す。**アウトラインと本文がズレた時点で価値が消える**
- 対象は設計・調査結果・提案など**構造を持つ文書**。1〜2画面で読み切れるメモには付けない
- **ドキュメントは実際に困ってから足す**。先回りして網羅せず、未決事項は「まだ決めていないこと」として明示的に残す

## Document Reference Guidelines

- **共有ドキュメントは `~/.ai_agent/docs/` に置く**。Claude Code・Codex の双方から同じパスで参照する
  - トピックごとに1ディレクトリを切り、その中に `public.md` と `private.md` を並べる（例: `docs/team/public.md`, `docs/team/private.md`）
- **`docs/{topic}/public.md` を読んだら、同ディレクトリの `private.md` の有無を必ず確認し、あれば併せて読む**
  - public 側 = 公開可能な仕組み・ルール本体。private 側 = 識別子・社内固有名詞・実名・社内制度などの**秘匿部分の差分のみ**（本文の複製はしない）
  - 記述が競合する場合は **private 側を優先する**
  - **private 側が無い環境でも public 側だけで動作すること**。private の存在を前提にした処理を書かない
- `private` で始まるファイルは chezmoi が管理するが **git では追跡しない**。**秘匿情報を public 側に書かない**
  - 新しくドキュメントを作るときも、識別子・固有名詞は private 側へ切り出す
- **`docs/` 配下を書き換えるときは chezmoi のソース側を編集する。** `~/.ai_agent/` を直接編集すると、次の `chezmoi apply` で消える
  - private 側は git 追跡外で**履歴が無く、消えたら復旧できない**。public 側と違い取り返しがつかない
  - 手順（パスは環境ごとに違うのでコマンドで解決する）:
    ```bash
    src=$(chezmoi source-path ~/.ai_agent/docs/{topic}/private.md)  # ソースの実体を得る
    # $src を編集する
    chezmoi apply ~/.ai_agent/docs/{topic}/private.md               # ターゲットへ反映
    ```
  - 先にターゲット側を編集してしまった場合は `chezmoi re-add ~/.ai_agent/docs/{topic}/private.md` で取り込む
  - **chezmoi が無い環境（`command -v chezmoi` が空、または `source-path` が `not in destination directory` を返す）ではターゲットを直接編集してよい**
- **人・チャンネル・組織を扱う作業の前に `~/.ai_agent/docs/team/public.md` を読む**（Slack 投稿、対外メッセージ作成、レビュー依頼など）
  - 表に無いメンバー・チャンネル・GitHub ユーザーに接触したら、その場で private 側へ追記する（追記ルールは `docs/team/public.md` に定義）

## Learning Capture Guidelines

- **ユーザーの指摘・訂正を受けて行動を変えたら、その場で1ファイル書き出す**
  - **Claude Code はネイティブの memory 機構がこれを兼ねる。**そちらに書けばよい（二重に書かない）
  - **Codex はネイティブの蓄積先が無い**（`~/.codex/memories_1.sqlite` は空で、markdown の読み書き口も無い）。
    必ず `~/.ai_workspace/memory/{kebab-case-slug}.md` に書く
  - 書式は Claude の memory と揃える。**昇格スキルが両方を同じ形で読むため、ズレると片方が拾われなくなる**

    ```markdown
    ---
    name: <kebab-case-slug>
    description: <1行要約。関連性の判断に使う>
    metadata:
      type: user | feedback | project | reference
    ---

    <事実。feedback / project は **Why:** と **How to apply:** を続ける>
    ```

  - 既に同じ趣旨のファイルがあれば**新規作成せず、そのファイルを更新する**
- **溜めた学びは `ore-improve` で恒久ルール（`core.md` / `CLAUDE.md` / `AGENTS.md` / skill / docs）へ昇格させる**
  - **書きっぱなしにしない。**溜めるだけでは行動は変わらない
  - 昇格したファイルには frontmatter に `promoted: <日付> <昇格先>` が入り、次回の抽出から外れる

## Production Operation Guidelines

- **本番環境（prd）への操作は、必ず実行前に plan を提示して承認を得る**
  - 対象操作: ワークフロー/ジョブの submit・terminate・resume、Cloud Run のトラフィック変更・デプロイ、本番テーブルへの INSERT/UPDATE/DELETE、その他本番の状態を変える操作すべて
  - plan には「何を・どの順で・何に影響するか」を明記し、`y/n` で承認を取ってから実行する
  - **一連の作業の流れで自明に見えても、勝手に submit・実行しない**。包括的な承認（「進めて」等）があっても、個々の本番操作の直前に都度 plan を見せて確認する
  - 既に同じ処理が実行中でないか（重複実行にならないか）を submit 前に必ず確認する
- **apply・デプロイを実行する CI ワークフローがあるリポジトリでは、IaC の適用・デプロイを手元から実行しない**（**環境は prd に限らない**。dev / stg も同じ）
  - `terraform apply` / 手動デプロイ / ローカルソースのビルド投入をしない。**PR の手順書にも書かない**
  - 手元で回してよいのは `plan` / `validate` / `lint` など**読み取り側だけ**。切り戻しも revert PR を同じ経路で流す
  - **理由は承認の有無ではなく追跡性。** 手動適用は state と CI の実行結果がずれ、誰が何を当てたか追えなくなる
  - 「進めて」等の**包括的な指示では実行しない。個別に明示されたときだけ、影響を提示して確認してから実行する**（下記「PR のマージは実行しない」と同じ型）
  - 判定は「apply・デプロイを行う CI ワークフローが存在するか」で行う。**テストのみの CI しか無いリポジトリは対象外**
- **読み取り専用の操作（SELECT、describe、logging read、workflow の get/list 等）は承認不要**

## Branch & PR Guidelines

- **1ブランチ = 1PR** — 1つのブランチには PR を1つしか作成しない
- **マージ済みブランチへのコミット禁止** — マージ済み PR のあるブランチには新しいコミットをしない。新しいタスクは必ず新しいブランチを作成する
- **オープン PR ブランチへの追加コミット** — レビュー対応など正当な理由がある場合のみ、ユーザーに確認した上で許可する
- **PR のマージは実行しない** — 実行タイミングの判断はユーザーの責務（環境によっては自動デプロイまで連鎖する）。可否の分類とコマンドの提示までにとどめ、「マージして良いものはマージ」のような包括的な指示があっても実行しない

## Notion タスク管理

- **Notion のタスクを操作する前に、必ず `~/.ai_agent/docs/task-system/public.md` を読む**（private 側があれば併せて読む。上記 Document Reference Guidelines に従う）
  - トリガー例: 「タスク登録して」「これタスクにしといて」「今の状況は？」「順位整理して」「〇〇終わった」「クオータ切り替えて」
  - 読まずに Notion のタスク DB を触らない
  - **`notion-search` で対象 DB を探さない**。旧 DB に誤って書き込む事故が起きる。DB は private 側に記載の id で指定する
  - private 側が無い、または id が未記入なら作業を止めて確認する
